このプロジェクトのポイント

担当範囲

現行版では、設計・実装・改善を本人が主体となって担当したプロジェクトです。

主な技術

Next.js / TypeScript / Prisma / PostgreSQL / Docker を用いて、フロントエンドからAPI・DBまで一貫して構築しています。

課題解決

教室予約をタイムラインで可視化し、予約申請・承認・履歴確認までを一つのWebアプリで完結できるようにしました。

アピールポイント

現場フィードバックを取り入れながら改善し、UI・API・データ設計を一体で見直した点が強みです。

プロジェクトの背景と進め方

  • 本プロジェクトでは、画面実装だけでなく、API設計・データベース設計・運用を意識した構成まで一貫して取り組んでいます。
  • 開発開始時は 5〜6 人規模のチーム開発で進めていましたが、その後、現行版の設計・実装・改善を中心となって引き継ぎました。
  • 利用者である教員に複数回見せてフィードバックを受け、要件変更に対応しながら画面構成や運用フローを改善しました。実務に近いアジャイルな開発経験として取り組んでいます。
  • Docker、Prisma、Next.js を組み合わせ、開発環境構築からデータ管理まで含めて再現性のある構成を意識しました。

工夫した点とアピールポイント

現場フィードバックを前提にした改善

  • 学校で利用する教員に実際に触ってもらい、画面や機能に対するフィードバックを受けて改善を行いました。
  • 初期段階ではカレンダーベースの予約画面を想定していましたが、フィードバックを踏まえて部屋ベースで状況を見られるタイムライン構成へ調整しました。
  • 予約申請だけでなく、教員側で確認・承認しやすい管理画面も追加し、UI の見やすさと運用しやすさを優先して改善しています。

データ構造と保守性を意識した設計

  • データベース操作には Prisma を採用し、スキーマを見通しやすく保ちながら変更しやすい構成を意識しました。
  • schema.prisma にモデル定義を集約することで、部屋・時間枠・予約・ステータスの関係を把握しやすい構成にしています。
  • マイグレーション履歴を通じて、予約ステータスやキャンセル状態の追加を段階的に反映できる構成になっています。

直面した課題と学び

予約時間の扱いと重複制御

  • 予約が重複しないように制御する実装に苦労しました。
  • 特に、Docker 上のデータベースとクライアント側で扱う日時の基準がずれ、予約処理が意図通りに動かない問題の切り分けに時間を要しました。
  • UTC と日本時間の差異により、ミリ秒単位の差で別時刻として扱われ、フロントエンド上では成功したように見えてもデータベース登録に失敗するケースがあり、日時処理の重要性を学びました。

データベース操作からフロントエンドへの連携

  • データベースへ保存し、取り出し、その結果を画面へ反映する一連の流れを構築する中で、全体のデータフローを把握することに注力しました。
  • Prisma を通じてどのように PostgreSQL へアクセスし、その結果が Next.js の API を経由して画面に返るのかを実践を通して理解しました。
  • エラー発生時に、原因がフロントエンド・API・ORM・DBのどこにあるのかを切り分けるトラブルシューティングの経験を積むことができました。

今後の展望

今後は、教室予約機能に加えて、校内掲示やイベント情報の共有もオンライン上で完結できるように発展させたいと考えています。

  • 紙で掲示されているチラシや告知をデジタル化し、学生がいつでも確認できる仕組みに広げる。
  • 他専攻の学生とも接点を持ちやすくし、校内コミュニケーションや交流のきっかけになるアプリへ発展させる。
  • 将来的には学校の後輩へ引き継ぎ、校内で継続利用されるシステムとして育てることを目指しています。

1. プロジェクト概要

アプリケーションで確認できた機能

  • タイムライン形式での教室予約状況表示（src/app/timeline/page.tsx）

  • 予約ステータス管理（PENDING, APPROVED, REJECTED, CANCELLED）
  • 管理画面での予約承認・却下（src/app/adminPanel/page.tsx）
  • 予約履歴の閲覧・ステータス別表示（src/app/History/page.tsx）
  • 予約キャンセル機能（画面によって PATCH または DELETE を使用）
  • トースト通知（sonner）
  • キャンセル確認ダイアログ（AlertDialog）

4.2 モデル定義

Reservation

フィールド 型 制約 説明
id String PK, uuid 予約ID
slotId / roomId Int FK 時間枠ID / 部屋ID
personName / grade / className String 必須 予約者情報

ReservationStatus (Enum)

値 意味
PENDING 仮予約（申請中）
APPROVED 承認済み
REJECTED 却下済み
CANCELLED キャンセル済み

5. API仕様

5.1 エンドポイント一覧

メソッド パス 機能
GET / POST /api/reservations 予約一覧取得 / 単一・一括予約作成
PATCH / DELETE /api/reservations/[id] ステータス更新 / 予約削除
POST /api/reservations/bulk 一括予約作成
PATCH /api/reservations/status 承認・却下
GET /api/timeline タイムラインデータ取得

5.2 APIごとの確認事項

  • POST /api/reservations/bulk: new Map() により重複スロットを排除。APPROVED の既存予約を対象に重複チェックを行い、Prisma P2002 のエラーハンドリングを実装。
  • PATCH /api/reservations/status: APPROVED 時は同一 slotId・roomId の承認済み予約を確認。REJECTED 時は対象予約を物理削除し 204 を返却。
  • GET /api/timeline: クエリパラメータ date=YYYY-MM-DD が必須。該当日の schedule がなければその場で作成。1日 7 コマ（90分）の枠を生成。

5.3 APIフロー

[ブラウザ / fetch]
   ↓  HTTPリクエスト (GET /api/...)
[Next.js API Route Handler]
   ↓  PrismaでDBからデータ取得
   ↓  JSON形式に変換
   ↓  NextResponseで返却
[ブラウザ / fetch]
   ↓  JSONを受け取り画面に表示

6. 画面構成

※ 実際の画面イメージについては、前半の「画面イメージ」セクションを参照してください。

6.1 ページ一覧と機能

パス コンポーネント 内容
/ または /timeline TimelinePage タイムライン画面。カレンダー、フロアフィルター、予約実行UIを備え、スロット選択後に一括予約を実行。
/History HistoryPage 予約履歴画面。ステータス別（PENDING, APPROVED 等）にタブで一覧表示し、キャンセル機能を提供。
/adminPanel AdminPanelPage 予約承認管理画面。申請中予約のみを取得し、承認・却下操作を行う。

7. 主要コンポーネント

ReservationTimeline.tsx

  • 7コマ分のテーブルを描画し、部屋列は sticky left-0 で固定。
  • 予約済みセルには用途・予約者名・学年/クラス・キャンセルボタンを表示。
  • 空きセルはクリックで選択状態を切り替え。

ReservationDialog.tsx

  • 予約入力ダイアログ。必須入力（学年, カレッジ, 予約代表者名）と任意入力（用途名, 利用人数, 備考）を収集。
  • 学年やカレッジはプルダウン選択肢として提供。

8. シードデータ

prisma/seed.ts に基づき、初期データとして以下の構成を作成しています。

  • 時間枠: 09:10 開始〜 21:20 終了までの全7コマ（各90分）。
  • 教室データ: レクチャー室、スタジオ、MACルーム、ホールなど全37件の部屋情報（定員設定付き）。
  • シード処理: 当日から 30 日分の schedule と slot を自動生成。

9. Docker構成

docker-compose.yml に基づき、データベース環境をコンテナ化しています。

  • PostgreSQL 14 を使用し、永続化ボリューム db をマウント。
  • アプリケーション本体（Next.js）用の Dockerfile.next.js および本番用 Dockerfile もリポジトリ内に用意。
